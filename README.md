### 1.2. Задание по кейсу № 3 (текст из задания)

> Необходимо создать систему, классифицирующую аудио‑сообщения из Telegram по заранее определённым категориям тематики.
>
> 1. Развлечения — сообщения, связанные с культурными событиями, фильмами, музыкой и т.д.
> 2. Образование — сообщения, касающиеся учебных материалов, курсов, лекций и т.д.
> 3. Технологии — сообщения, обсуждающие новинки в области технологий, гаджетов и т.д.
>
> На вход подаются голосовые сообщения, на выход — метка тематики.
>
> Использовать TTS (Text‑to‑Speech) для синтеза аудио с различными тематиками на основе текстовых данных, чтобы обогатить тренировочный датасет.

### 1.3. Реализованная схема решения

В проекте используется Telegram-бот на `aiogram`: он получает голосовое сообщение либо аудиофайл, проверяет его длительность и размер, преобразует через `ffmpeg`, распознаёт речь с помощью `faster-whisper`, передаёт транскрипцию текстовому классификатору и возвращает распознанный текст с тематикой и оценкой уверенности. Доступные прикладные метки обученного классификатора — **«образование», «развлечения», «технологии»**; предусмотрено также значение **«другое»** для некоторых неопределённых случаев.

Репозиторий включает воспроизводимый эксперимент по подготовке новостей Lenta.ru и обучению классификатора, пробный TTS-набор и тестовую проверку связки ASR → классификатор.

## 2. Data - Хоменко Дмитрий

### 2.1. Реально использованный датасет

Использован Lenta.Ru-News-Dataset v1.1. Исходный архив содержит **800 975 новостей** с полями `url`, `title`, `text`, `topic`, `tags`, `date`.

Тематические метки трёх целевых классов получены **автоматически** на основе редакционных рубрик/тегов и правил по заголовкам; это *weak labels*, а не независимая экспертная разметка. При подготовке отфильтрованы нерелевантные темы, конфликты правил, короткие тексты, аномальные даты, точные дубликаты и ранее просмотренные объекты. Для обучения используется не весь корпус, а **3 615** подготовленных текстов; в модель передаются первые **140 слов тела статьи** (без заголовка, рубрик и тегов).

| Часть | Годы | Объектов | На класс |
|---|---|---:|---:|
| Train | 1999–2017 | 3 066 | 1 022 |
| Validation | 2018 | 183 | 61 |
| Test | 2019 | 366 | 122 |

### 2.2. Предобработка и классификатор

Реализованы приведение текста к нижнему регистру, замена `ё` на `е` при нормализации, схлопывание пробелов для поиска дублей, стандартная токенизация слов и `TF-IDF` с униграммами и биграммами. Словарь имеет **40 000 признаков**. Лемматизация и удаление стоп-слов не используются. Векторизатор обучается только на Train; проверяются точные пересечения данных между частями. Алгоритм классификации **не использует трансформеры**.

Сопоставлены `LogisticRegression` (Validation macro-F1 **0,9619**) и `MultinomialNB` (Validation macro-F1 **0,9673**). Выбран **TF-IDF + MultinomialNB**; на отложенном Test получены **Accuracy 0,9754 (97,54%)** и **macro-F1 0,9756**.

### 2.3. Анализ ошибок и постобработка

На Test обнаружены **9** расхождений предсказаний с предварительными метками из **366** случаев. Репозиторий содержит матрицу ошибок и диагностический аудит **30** примеров с неоднозначными/ошибочными категориями. При этом подробный разбор всех девяти конкретных ошибочно классифицированных текстов в опубликованном отчёте не приведён.

Классификатор возвращает метку и числовую уверенность; пустой текст, полностью неизвестные словарю слова или оценка ниже установленного порога могут дать тему «другое».

### 2.4. TTS-пилот

На основе подготовленных текстов создано **27** синтетических WAV-записей (один голос macOS Milena, mono, 16 кГц; около **607 секунд** суммарно). На девяти аудио из Test проведена оценка цепочки ASR → классификация; результат указан в разделе Speech.

## 3. MLOps — Плотников Владислав

### MLOps и инфраструктура

Инфраструктурная часть проекта обеспечивает совместную разработку, воспроизводимость окружения, автоматический контроль качества кода, объединение компонентов в единый сервис и его доставку на сервер.

#### Структура репозитория

Проект размещён в монорепозитории. Код разделён по назначению:

| Каталог                    | Назначение                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| src/newsbot/               | общий пакет: контракт данных, распознавание речи, классификатор — рабочий код, используемый сервисом |
| services/bot/              | Telegram-бот                                                                                         |
| ml/notebooks/, ml/scripts/ | эксперименты, подготовка данных, обучение и оценка моделей                                           |
| ml/data/, ml/models/       | данные и артефакты моделей; в Git не хранятся, версионируются через DVC                              |
| tests/                     | автоматические тесты                                                                                 |
| deploy/, compose.yaml      | развёртывание на сервере                                                                             |

Эксперименты ведутся в ноутбуках; после выбора модели её код переносится в пакет src/newsbot/ и становится доступен сервису.

#### Окружение и зависимости

Зависимости управляются менеджером uv. Файл uv.lock фиксирует точные версии всех пакетов, благодаря чему окружение у всех участников, в CI и в продакшене идентично. Зависимости разделены на группы:

| Группа   | Состав                               | Назначение                                         |
| -------- | ------------------------------------ | -------------------------------------------------- |
| основные | faster-whisper, scikit-learn, joblib | работа моделей; требуются везде, включая продакшен |
| bot      | aiogram, pydantic-settings           | сервис бота                                        |
| ml       | Jupyter, pandas, matplotlib, DVC     | эксперименты и работа с данными                    |
| dev      | pytest, ruff, pre-commit             | разработка и проверки                              |

В образ продакшена устанавливаются только основные зависимости и группа bot. Новые зависимости добавляются командой uv add, изменённые pyproject.toml и uv.lock фиксируются в репозитории вместе с кодом.

#### Формат работы с Git

Используется модель с двумя постоянными ветками и рабочими ветками участников и задач:

| Ветка         | Назначение                                                                                   |
| ------------- | -------------------------------------------------------------------------------------------- |
| main          | стабильная версия; каждое изменение автоматически разворачивается на сервере                 |
| dev           | ветка интеграции: в ней объединяются изменения участников и проверяется их совместная работа |
| именные ветки | личная рабочая область участника (эксперименты, ноутбуки)                                    |
| feature/…     | ветки под конкретную задачу (например, feature/bot, feature/deploy)                          |

Правила работы:
- Изменения попадают в dev и main только через Pull Request; прямая запись в эти ветки не допускается.
- Pull Request принимается после успешного прохождения CI.
- Данные и модели в Git не хранятся. Их изменения фиксируются через DVC: в Git попадает файл-указатель .dvc с отпечатком содержимого, сами файлы выгружаются во внешнее хранилище.
- Секреты (токен бота, ключи доступа) хранятся в файле .env и в секретах GitHub.
#### Контроль качества

Контроль качества выполняется на двух уровнях.

Перед коммитом (pre-commit) локально запускаются: линтер и форматирование кода (ruff), очистка выводов ноутбуков (nbstripout), проверка на секреты и конфликты слияния, запрет добавления файлов размером более 1 МБ — это предотвращает попадание весов моделей и датасетов в Git. Версия ruff в pre-commit совпадает с версией в uv.lock, поэтому локальная проверка и CI дают одинаковый результат.

В CI (GitHub Actions) на каждый Pull Request выполняется:

| Шаг                             | Что проверяется                             |
| ------------------------------- | ------------------------------------------- |
| uv sync --locked                | окружение собирается строго по lock-файлу   |
| ruff check, ruff format --check | ошибки в коде и единообразие форматирования |
| pytest                          | автоматические тесты всех компонентов       |
| сборка Docker-образа            | образ сервиса собирается без ошибок         |

#### Интеграция компонентов

Проект объединяет несколько модулей: распознавание речи (Speech), классификацию тематики (Data) и сервис. Интеграция построена на следующих принципах.

Контракт данных. Взаимодействие между частями зафиксировано в src/newsbot/schemas.py: распознавание речи возвращает структуру Transcription (текст и длительность аудио), классификатор — TopicPrediction (тема и уверенность в диапазоне 0..1). Сервис зависит только от контракта, поэтому модели могут заменяться без изменения кода бота. Изменение контракта требует согласования участников.

Единый интерфейс моделей. Любой классификатор реализует метод predict(text) -> TopicPrediction и подключается через фабрику build_classifier(). Выбор реализации выполняется настройкой (CLASSIFIER_BACKEND): заглушка для разработки без модели или обученный TF-IDF классификатор. Распознавание речи (WhisperASR) аналогично настраивается размером модели, устройством и режимом предобработки.

Конвейер обработки. Сервис последовательно соединяет компоненты:
Голосовое сообщение
  → проверка длительности и размера
  → предобработка ffmpeg (WAV 16 кГц, mono, шумоподавление)
  → распознавание речи (faster-whisper)
  → классификация тематики 
  → ответ пользователю

 Артефакты моделей. Веса распознавания речи хранятся публично и загружаются по имени из HuggingFace при первом запуске, после чего кэшируются. Обученный классификатор хранится в DVC и подключается к сервису как внешний файл: обновление модели не требует пересборки сервиса.

 Конфигурация. Все параметры сервиса (токен, модели, пороги, лимиты) задаются переменными окружения в файле .env; шаблон с описанием параметров — .env.example. Один и тот же код работает локально и на сервере с разными настройками.

 Кроссплатформенность. Часть команды работает на Windows, поэтому чтение файлов выполняется с явным указанием кодировки UTF-8 (отдельный тест контролирует это правило), а пакетная обработка поддерживает формат голосовых сообщений Telegram (.ogg).

#### Сервис Telegram-бота

Бот реализован с помощью aiogram 3 и состоит из модулей конфигурации, конвейера обработки, текстов и обработчиков сообщений. Основные решения:
 - Длительность и размер аудио проверяются до загрузки файла; лимит Bot API на скачивание составляет 20 МБ.
 - Модели выполняются в отдельном потоке, а число одновременно обрабатываемых сообщений ограничено, что сохраняет отзывчивость бота.
 - Модели загружаются при запуске сервиса: ошибка конфигурации обнаруживается сразу, а первое сообщение пользователя не ожидает загрузки.
 - Пустая речь, ошибки модели и неопределённая тема обрабатываются явно и сопровождаются понятным ответом.
 - На каждое сообщение записывается структурированный лог: время распознавания и классификации, тема, уверенность.

Логика бота покрыта тестами, не требующими доступа к Telegram и загрузки моделей.

#### Контейнеризация и развёртывание

Сервис поставляется в виде Docker-образа, содержащего только зависимости продакшена и ffmpeg; процесс запускается от непривилегированного пользователя. 

Развёртывание автоматизировано:
Pull Request принят в main
  → GitHub Actions: сборка образа → GitHub Container Registry (тег по коммиту)
  → подключение к серверу по SSH 
  → обновление контейнера
  → проверка готовности сервиса 
  → при сбое откат на предыдущую версию

| Свойство             | Реализация                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------ |
| Обновление           | автоматически при каждом изменении main                                                    |
| Автоматический откат | если контейнер завершился с ошибкой или не стал готов за отведённое время                  |
| Ручной откат         | запуск workflow с указанием коммита; используется ранее собранный образ                    |
| Данные на сервере    | .env, файл классификатора и кэш весов распознавания хранятся вне образа                    |
| Безопасность         | SSH-ключ хранится в секретах GitHub; токен реестра действует только во время развёртывания |
| Использование диска  | на сервере сохраняются только текущая и предыдущая версии образа                           |

## 4. Speech — Иван Исайкин

### 4.1. Модуль распознавания речи

В репозитории реализован класс [`WhisperASR`](https://github.com/TaurineMerge/news_classifier_bot/blob/main/src/newsbot/asr.py) на базе `faster-whisper` (CTranslate2). Он принимает аудиофайл и возвращает объект `Transcription` с распознанным текстом и длительностью аудио. Сервис поддерживает загрузку весов по имени с Hugging Face, кэширование и офлайн-режим `local_files_only=True`, если веса уже имеются локально. 
### 4.2. Предобработка и устойчивость

Перед распознаванием аудио обрабатывается через `ffmpeg`: выделение аудиодорожки, перевод в WAV PCM16, 16 кГц, mono; доступны режимы шумоподавления `auto`/`on`/`off`, фильтры `arnndn` (при наличии подходящих весов) и `afftdn`. Есть обработка ошибок входного файла и `ffmpeg`, удаление временного WAV. В `WhisperASR` предусмотрено VAD и выбор CPU/CUDA; в режиме `auto` есть переход на CPU при определённых ошибках CUDA-библиотек. 
### 4.3. Проверка ASR

Реализованы изолированные тесты ASR-пайплайна без обязательного скачивания больших моделей, а также скрипты для батчевой транскрибации и сравнения режимов предобработки. В отчёте Data-команды приведена проверка общей связки на **9 синтетических тестовых аудио** (один голос; Whisper tiny на CPU/int8): micro-WER **0,3861**, определение правильной темы по предварительным меткам **8 из 9**.
