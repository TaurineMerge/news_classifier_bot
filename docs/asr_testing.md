# ASR testing

Приёмка ASR-задачи: как прогнать тесты, как читать их статусы, как смотреть результаты батчей и в каких единицах мерить.

## Запуск

Из корня проекта, с `PYTHONPATH`, указывающим на корень (чтобы резолвился `src.newsbot.*`):

```powershell
$env:PYTHONPATH="."
python -m pytest tests/test_asr_pipeline.py -v
```

`python -m pytest`, а не голый `pytest`, — чтобы использовался тот же интерпретатор, где стоят зависимости, и корректно определялся rootdir/conftest.

Требуется установленный `pytest` (проверка: `python -c "import pytest; print(pytest.__version__)"`).

## Изоляция unit-тестов

Unit-тесты не требуют сети, GPU, установленного `ffmpeg`, реальных весов модели и больших аудиофайлов. Внешние вызовы (`subprocess.run`/`ffmpeg`, `shutil.which`, создание `WhisperModel`, проверка CUDA) подменяются моками. Это свойство, а не этап отладки: тесты должны проходить на голой машине. Поэтому `SKIPPED`/`PASSED` без железа — норма, а не баг.

## Как читать статусы

- `PASSED` — поведение соответствует ТЗ.
- `SKIPPED` на импортах (`asr` / `audio_preprocess` / `schemas`) — модуль не импортируется. Причина почти всегда в путях/стиле импортов или `PYTHONPATH`, а не в логике: проверь, что conftest добавляет в `sys.path` корень проекта и что внутренние модули используют относительные импорты (`from .schemas import`), а снаружи пакет зовётся `src.newsbot.*`.
- `FAILED` — смотреть конкретный `assert` и строку трейсбека.

## Связь ленивой загрузки и device-тестов

Модель грузится лениво (внутри `transcribe`), а не в конструкторе. Для текущих тестов это не рассинхрон: device-тесты сначала вызывают `transcribe(...)`, и только после этого проверяют аргументы создания модели — к этому моменту мок уже дёргнулся. Явный `device="cuda"` без CUDA бросает ошибку ещё в резолвере устройства, до загрузки модели, и тест ловит её вокруг конструктора. Если тесты на устройство правятся — учитывать, что проверка вызова модели должна идти после `transcribe`, а не после `__init__`.

## Интеграционные тесты

Тесты, которым нужен реальный `ffmpeg`/реальная модель, помечаются `@pytest.mark.integration` / `@pytest.mark.slow` и не входят в быстрый прогон. Основной `pytest` обязан проходить без них.

## Просмотр результатов батча

Результаты батч-транскрибации пишутся в CSV (`utf-8-sig`) и JSON (`utf-8`).

Важно для просмотра: `utf-8-sig` корректен на диске, но двойной клик по `.csv` в Excel на русской Windows показывает кракозябры — Excel для `.csv` по умолчанию берёт системную CP1251 и игнорирует BOM. Это особенность просмотра, а не повреждение данных: в JSON кириллица цела всегда.

Корректные способы посмотреть текст:

1. JSON — редактор/браузер/парсер читают UTF-8 напрямую;
2. `python scripts/view_csv.py results/<файл>.csv [N]` — вывод в консоль + генерация `.html` с `charset=utf-8`, который Excel открывает с нормальной кириллицей;
3. Excel → *Данные → Из текста/CSV* → кодировка файла `65001 : Unicode (UTF-8)`.

## Сравнение режимов денойзинга

Сравнение `off` vs `auto` валидно только когда прогоны отличаются **исключительно** флагом `--denoise`, а устройство, офлайн-режим и лимит файлов идентичны. Разные прогоны в разных условиях несопоставимы.

```powershell
$env:PYTHONPATH="."; $env:HF_HUB_OFFLINE="1"

python scripts/batch_transcribe.py --max-files 20 --device cpu --denoise off --output-csv results/t_no.csv --output-json results/t_no.json
python scripts/batch_transcribe.py --max-files 20 --device cpu --denoise auto --output-csv results/t_yes.csv --output-json results/t_yes.json

python scripts/compare_results.py results/t_no.json results/t_yes.json
```

`compare_results.py` читает JSON и сводит по каждому файлу статус (`совпадает` / `различается` / `ОШИБКА`) и время. При интерпретации сначала смотреть колонку ошибок: если в `t_yes` появились ошибки, которых нет в `t_no`, это сбой денойзера, а не эффект шумодава. Только при нулевых ошибках разница `совпадает/различается` читается как реальное влияние денойзинга.

## Единицы метрик

- `duration_sec` — длительность аудио, секунды.
- `processing_sec` — wall-clock время одного `transcribe` (предобработка + инференс), секунды.
- `rtf` (real-time factor) = `processing_sec / duration_sec`, безразмерно (сек/сек). `rtf < 1` означает, что файл обрабатывается быстрее своей длительности.
- Среднее время по батчу — `mean(processing_sec)`, секунды на файл; итог по массиву — сумма `processing_sec`, секунды.

Все времена измеряются `time.perf_counter()` вокруг вызова `transcribe`. При оформлении результатов указывать именно эти определения, чтобы цифры из разных прогонов были сопоставимы.
