# ASR pipeline

Распознавание речи в проекте строится на двух этапах: предобработка аудио через `ffmpeg` и инференс через `faster-whisper` (движок CTranslate2). Контракт между этапами и внешним миром зафиксирован в `src/newsbot/schemas.py` и не меняется без отдельного согласования.

## Схема

```text
входной аудиофайл (.ogg / .opus / .mp3 / .wav / .m4a)
  → ffmpeg: конвертация в WAV 16 kHz mono PCM s16le
  → ffmpeg: опциональный денойзинг (arnndn → afftdn → none)
  → faster-whisper small: инференс (VAD включён)
  → Transcription(text, audio_duration_sec)
```

## Зачем ffmpeg

Три причины, все обязательны для корректной работы:

1. **Гарантия формата.** `faster-whisper` стабильно принимает WAV 16 kHz mono PCM s16le. Прямая подача произвольного контейнера/кодека не даёт такой гарантии.
2. **Денойзинг.** Шумоподавление делается фильтрами `ffmpeg` до инференса.
3. **Изоляция декодера.** Конвертация в чистый WAV убирает из пути `faster-whisper` парсинг метаданных исходного контейнера (в частности mp3), что исключает класс ошибок декодера на уровне контейнера.

`ffmpeg` — системная зависимость, не ставится через `pip`/`uv`.

### Установка и проверка

Linux (Debian/Ubuntu):

```bash
sudo apt update && sudo apt install -y ffmpeg
```

Windows:

```powershell
winget install Gyan.FFmpeg
# после установки перезапустить терминал
```

Проверка наличия и фильтров:

```bash
ffmpeg -version
ffmpeg -hide_banner -filters | grep -E "afftdn|arnndn"   # linux
ffmpeg -hide_banner -filters | Select-String "afftdn|arnndn"   # windows
```

## Денойзинг

Режимы (`denoise_mode`):

- `auto` (по умолчанию) — использовать денойзинг, если возможно;
- `on` — денойзинг обязателен, иначе ошибка;
- `off` — только конвертация, без шумоподавления.

Приоритет фильтра в `auto`/`on`:

1. `arnndn` — нейро-денойзер RNNoise, требует файл весов и поддержку фильтра в сборке `ffmpeg`;
2. `afftdn` — встроенный FFT-денойзер, не требует внешних файлов;
3. `none` — если в `auto` ни один недоступен, выполняется только конвертация (с предупреждением в лог).

Веса RNNoise по умолчанию: `ml/models/rnnoise/bd.rnnn`. Путь переопределяется аргументом `rnnoise_model_path` или env `RNNOISE_MODEL_PATH`. Веса не коммитятся в git.

> Статус `arnndn` зависит от сборки `ffmpeg`: фильтр должен быть скомпилирован с `--enable-librnnoise`, и формат весов должен совпадать с версией библиотеки. Если `arnndn` присутствует в списке фильтров, но падает при инициализации, пайплайн корректно откатывается на `afftdn` (в режиме `auto`). Это штатный fallback, а не ошибка конфигурации.

## Устройство и тип вычислений

Параметр `device` по умолчанию — `auto`. Значения `"gpu"` не существует; корректные имена — `"cpu"`, `"cuda"`, `"auto"`.

Логика `auto`:

- если CUDA доступна и модель на ней загружается — `device="cuda"`, `compute_type="float16"`;
- иначе — `device="cpu"`, `compute_type="int8"`.

Явный `device="cuda"` fallback не делает: если CUDA недоступна, бросается понятная ошибка (осознанный запрос пользователя). Явный `device="cpu"` не обращается к GPU.

### Graceful-fallback по ошибке загрузки библиотек

Доступность GPU по драйверу (`ctranslate2.get_cuda_device_count() > 0`) не гарантирует, что рантайм-библиотеки CUDA нужной мажорной версии реально загрузятся. Например, при установленном CUDA 13 и CTranslate2, собранном под cuBLAS 12, запрос cuda падает на загрузке `cublas64_12.dll`. Поэтому в режиме `auto` модель грузится и выполняется как попытка: при ошибке загрузки dll CUDA пайплайн переключается на следующий кандидат (`cpu`) и продолжает работу, записывая предупреждение в лог.

Ключевая деталь: CTranslate2 грузит cuBLAS/cuDNN **лениво**, при первом проходе по сегментам, а не при создании модели. Поэтому логика fallback обёртывает инференс (итерацию по `segments`), а не только конструктор модели.

### Принудительный CPU

Для воспроизводимости на CI/сдаче, независимо от мажора CUDA на хосте, выставь env:

```powershell
$env:NEWSBOT_FORCE_CPU="1"
```

Тогда `auto` и явный `cpu` идут по CPU без попытки обращения к GPU.

## Torch не используется

`faster-whisper` работает через CTranslate2, а не через PyTorch. GPU-ускорение не требует установки `torch`/`torchaudio`. Эти пакеты в зависимости запрещены.

## Где лежат веса и офлайн-режим

Веса whisper **не хранятся в git**. По умолчанию `faster-whisper` при первом запуске скачивает
модель по имени (`small`, `medium`…) с HuggingFace в стандартный кэш (`HF_HOME`, обычно
`~/.cache/huggingface`) и дальше берёт её оттуда. В Docker кэш вынесен в volume `whisper-cache`
и переживает пересборку образа.

Варианты:

- `download_root=...` — свой каталог для кэша;
- `model_size="ml/models/whisper-small"` — путь к папке с готовыми весами (`model.bin`, `config.json`, `tokenizer.json`, `vocabulary.txt`); такую папку версионируем через DVC, не через git;
- офлайн: `local_files_only=True` или env `HF_HUB_OFFLINE=1` — только когда веса уже на диске.

Для первого запуска на голой машине офлайн не включают — hub должен один раз скачать модель.

## Ленивая загрузка модели

`WhisperModel` создаётся не в конструкторе `WhisperASR`, а при первом обращении внутри `transcribe` (метод `_get_or_build`), с кэшированием по паре `(device, compute_type)`. Причина — ленивая загрузка CUDA-библиотек (см. выше): точка отказа находится в инференсе, поэтому и контроль, и fallback живут там же.

Сервисам, которым важен быстрый первый ответ и ошибка конфигурации при старте (бот), нужно вызвать `asr.load()` сразу после создания: модель загрузится заранее, а фолбэк cuda → cpu при первом инференсе продолжит работать.

## Диаризация

Не используется. Вход — голосовые сообщения с одним спикером, целевая задача — классификация темы, а не разделение говорящих. Зависимости для диаризации (`pyannote`, `speechbrain`, `nemo`) запрещены.

## Контракт

Публичный метод:

```python
def transcribe(self, audio_path: str) -> Transcription: ...
```

Возвращаемая структура (`src/newsbot/schemas.py`, `frozen` dataclass):

```python
Transcription(text: str, audio_duration_sec: float)
```

`schemas.py` — стык между компонентами. Менять поля `Transcription`/`TopicPrediction` без отдельного согласования нельзя. Служебная информация (выбранный денойзер, устройство, время обработки) выводится в логи, а не в контракт.

## Временные файлы

Промежуточный WAV создаётся в системной temp-директории (`tempfile.mkstemp`), удаляется после обработки — как при успехе, так и при ошибке (в `finally`). В репозиторий, в `src/`, в `ml/data/` временные файлы не пишутся.

## Логирование

В лог уровня `INFO`/`DEBUG` попадают: путь входа, выбранный денойзер, выбранное устройство и `compute_type`, время предобработки, время инференса, длительность аудио, длина текста, ошибки с контекстом. Полный распознанный текст в `INFO` не выводится.

## Ошибки

Базовый класс — `ASRError(RuntimeError)` (определён в `audio_preprocess.py`, реэкспортируется/используется в `asr.py`). Понятные ошибки выдаются на: отсутствие входного файла, отсутствие `ffmpeg`, ненулевой код возврата `ffmpeg`, отсутствие аудиопотока, недоступность денойзера в режиме `on`, явный `device="cuda"` без доступной CUDA, ошибку инференса.

## Публичный интерфейс WhisperASR

```python
class WhisperASR:
    def __init__(
        self,
        model_size: str = "small",
        device: str = "auto",
        compute_type: str | None = None,
        language: str = "ru",
        beam_size: int = 5,
        use_ffmpeg: bool = True,
        denoise_mode: str = "auto",
        rnnoise_model_path: Path | None = None,
        ffmpeg_bin: str = "ffmpeg",
        download_root: Path | None = None,
        ffmpeg_timeout_sec: float = 300.0,
    ) -> None: ...

    def transcribe(self, audio_path: str) -> Transcription: ...
```

Существующий сценарий `WhisperASR(model_size="small")` + `transcribe(path)` обязан работать без изменений: все новые параметры имеют значения по умолчанию.
